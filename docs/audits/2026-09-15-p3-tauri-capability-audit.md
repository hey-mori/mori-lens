# P3 Tauri Capability Audit

**Date:** 2026-09-15  
**Status:** COMPLETE (corrected 2026-09-15)  
**Tauri Version:** 2.x (resolved 2.11.5, tauri-build 2.6.3 during audit)

## Executive Summary

**Finding: Per-window command ACL implemented with least-privilege separation.**

The detail window is restricted to only 6 `detail_*` commands via Tauri v2 capability-based access control. High-risk commands (`library_secure_wipe`, `request_quit`, `set_autostart`, `save_settings`, `mori_send_item`) are denied to the detail window at the capability layer.

## Correction History

### Initial False-Green (2026-09-15 morning)

The initial audit incorrectly concluded that "custom commands cannot be capability-gated in Tauri v2." This was wrong.

**Root cause:** Failed to discover `AppManifest::commands()` API in tauri-build 2.6.3, which enables permission generation for custom commands.

**Correction (Phase 1, PR #561):** Implemented actual per-window capability restriction using:
1. `build.rs` with `AppManifest::commands()` to register all 44 commands
2. Per-window capability files (`main.json`, `detail.json`) with explicit command permissions
3. Autogenerated `allow-*`/`deny-*` permission files for each command
4. Verification script enforcing exact partition

### Core Permission Minimization (2026-09-15 afternoon)

Phase 1 implementation still granted overly broad core permissions via `core:default`.

**Problem:**
- Detail window had `core:default` which includes 9 default permission groups (app, image, menu, path, resources, tray, webview, window, event)
- Main window had `core:default` + `core:event:default` which includes unused emit/emit-to permissions
- Violated least-privilege principle: granted permissions not actually used

**Frontend API audit:**
- Detail window uses only `window.__TAURI__.core.invoke` (no event/window/menu/tray APIs)
- Main window uses `window.__TAURI__.core.invoke` and `window.__TAURI__.event.listen` (no emit/emit-to)

**Correction (Phase 2, PR #563):**
1. Removed `core:default` from detail window (now has 0 core permissions)
2. Replaced `core:default` + `core:event:default` in main window with minimal permissions:
   - `core:event:allow-listen` (used)
   - `core:event:allow-unlisten` (used)
3. Added verifier checks (steps 11-12) to enforce core permission constraints
4. Added regression tests for cargo check exit status handling

## Implementation

### Command Registration

**File:** `apps/lens/build.rs`

```rust
const COMMANDS: &[&str] = &[
    "check_ollama", "export_diagnostics", "get_diagnostics",
    // ... 44 total commands
    "detail_copy", "detail_open_in_library", "detail_read",
    "detail_request_explain", "detail_save", "detail_save_note",
];

fn main() {
    lens_build_stamp::emit();
    tauri_build::try_build(
        Attributes::new().app_manifest(AppManifest::new().commands(COMMANDS)),
    ).expect("failed to run tauri-build with app command manifest");
}
```

This enables tauri-build to autogenerate permission files for each command.

### Per-Window Capabilities

**Main Window:** `apps/lens/capabilities/main.json`
- 38 commands (all except `detail_*`)
- Core permissions: `core:event:allow-listen`, `core:event:allow-unlisten` (minimal, no emit)
- Has access to high-risk commands

**Detail Window:** `apps/lens/capabilities/detail.json`
- 6 commands only: `detail_copy`, `detail_open_in_library`, `detail_read`, `detail_request_explain`, `detail_save`, `detail_save_note`
- Core permissions: None (0 core permissions, only needs invoke)
- **Cannot** invoke high-risk commands

### Autogenerated Permissions

**Directory:** `apps/lens/permissions/autogenerated/`

44 TOML files, one per command. Each contains:
```toml
[[permission]]
identifier = "allow-library-secure-wipe"
description = "Enables the library_secure_wipe command without any pre-configured scope."
commands.allow = ["library_secure_wipe"]

[[permission]]
identifier = "deny-library-secure-wipe"
description = "Denies the library_secure_wipe command without any pre-configured scope."
commands.deny = ["library_secure_wipe"]
```

Capability files reference these identifiers (e.g., `"allow-detail-read"`).

5. Verify main ∪ detail == COMMANDS (exact partition)

8. Verify high-risk commands excluded from detail
9. Verify 44 autogenerated permission files exist
10. Verify no stale permission files
11. **Verify detail has NO core permissions**
12. **Verify main has ONLY minimal core permissions** (`core:event:allow-listen`, `core:event:allow-unlisten`)

## Security Properties

### High-Risk Commands Denied to Detail Window

The following commands are **capability-denied** to the detail window:
1. `library_secure_wipe` - Destructive data deletion
2. `request_quit` - Application lifecycle
3. `set_autostart` - System configuration
4. `save_settings` - Configuration mutation
5. `mori_send_item` - External data transfer

Even if malicious JavaScript were injected into the detail window, these commands would be rejected by the Tauri runtime with "command not allowed" errors.

### Least-Privilege Enforcement

**App commands:**
- **Main window:** Has access to all commands it needs (38 commands)
- **Detail window:** Has access to only the 6 commands it actually uses
- **No overlap:** main ∩ detail = ∅
- **Exact partition:** main ∪ detail = all 44 commands

**Core permissions (Phase 2 correction):**
- **Detail window:** 0 core permissions (only uses invoke, no event/window/menu/tray APIs)
- **Main window:** 2 core permissions (`core:event:allow-listen`, `core:event:allow-unlisten`)
- **Not granted:** `core:event:allow-emit`, `core:event:allow-emit-to` (unused), `core:default` groups (image, menu, path, resources, tray, webview, window)

### Evidence Level

- **IMPLEMENTED:** Capability configuration is in place
- **AUTOMATED CONFIG PASS:** `verify-tauri-capabilities.sh` validates configuration
- **STATIC/SOURCE VERIFIED:** Scripts parse actual source files, not hardcoded lists
- **BUILD VERIFIED:** `cargo check` validates capability schema
- **RUNTIME VERIFICATION:** Not performed (would require integration test harness)

The Tauri v2 framework enforces capability restrictions at runtime. Unauthorized command invocations are denied by the framework, but this has not been directly tested with a malicious payload.

## Tauri v2 Capability Model (Corrected)

### What Capabilities Control

Tauri v2 capabilities restrict:
1. **Plugin APIs:** filesystem, shell, dialog, clipboard, HTTP, etc.
2. **Core features:** window management, event system, etc.
3. **Custom commands:** When registered via `AppManifest::commands()` in build.rs

### Custom Command Permission Generation

When `build.rs` calls `AppManifest::new().commands(COMMANDS)`, tauri-build:
1. Generates `permissions/autogenerated/<command>.toml` for each command
2. Each file contains `allow-<command>` and `deny-<command>` permissions
3. Capability files can reference these permissions
4. Tauri runtime enforces the permissions at invocation time

### Verification

The implementation is verified by:
1. `scripts/verify-tauri-capabilities.sh` - Parses source files, checks partition
2. `scripts/check.sh` - Runs verifier as part of CI gate
3. `cargo check` - Validates capability schema
